# DDEV Structurizr

## Overview

C4 architecture docs with [Structurizr](https://structurizr.com) in [DDEV](https://ddev.com/) projects:
edit diagrams locally, export them to static SVG/Mermaid that render on GitHub,
so reading them never needs Docker or DDEV.

## Installation

```bash
ddev add-on get helga-agentur/ddev-structurizr
```

No restart needed: the add-on only adds host commands, which start their own containers on demand.

After installation, make sure to commit the `.ddev` directory to version control.

## Convention

One Structurizr workspace per Drupal module, named after the module.
The source always lives in the module:

```
web/modules/custom/my_module/
└── architecture/
    └── diagrams/workspace.dsl
```

The layout only decides where `ddev c4-export` writes the exports:

**`root` (default)**: one central folder in the project, sorted by module.
Works for every module, including contrib modules: they're installed by Composer and usually
git-ignored, so exports inside them would not be committed and get overwritten on updates.

```
architecture/
├── my_module/                   # generated by `ddev c4-export`, committed
│   ├── README.md                # index of all views, shown by GitHub
│   ├── SystemContext.svg
│   ├── SystemContext.md         # same view as Mermaid
│   └── ...
└── other_module/
```

**`module`**: next to the source, inside the module.

```
web/modules/custom/my_module/
└── architecture/
    ├── diagrams/workspace.dsl
    └── exports/
```

## Usage

| Command | Description |
| ------- | ----------- |
| `ddev c4 my_module` | Start Structurizr for one module and open the browser |
| `ddev c4` | Same, if there is only one workspace |
| `ddev c4 --list` | List modules that have a workspace |
| `ddev c4 my_module --stop` | Stop one module |
| `ddev c4 --stop-all` | Stop all Structurizr containers of the project |
| `ddev c4-export` | Export all modules |
| `ddev c4-export my_module` | Export one module |

Several modules can run side by side; each gets its own container and a free port.
The containers belong to the DDEV project: `ddev stop`, `ddev restart` and `ddev delete` stop them too.

Embed exports in a README.md or ARCHITECTURE.md (paths relative to that file), e.g. from the project root:

```markdown
## System context
![System context](architecture/my_module/exports/SystemContext.svg)

All views: [architecture/my_module/exports](architecture/my_module/exports/)
```

## Advanced Customization

Defaults work without any config. To change them, set values in `.ddev/.env.structurizr`
and commit that file:

```bash
ddev dotenv set .ddev/.env.structurizr --structurizr-layout=module
```

| Variable | Flag | Default | |
| -------- | ---- | ------- | - |
| `STRUCTURIZR_LAYOUT` | `--structurizr-layout` | `root` | `root` or `module` (see above) |
| `STRUCTURIZR_ARCHITECTURE_DIR` | `--structurizr-architecture-dir` | `architecture` | folder inside each module, and the central export folder (`root`) |
| `STRUCTURIZR_DIAGRAMS_SUBDIR` | `--structurizr-diagrams-subdir` | `diagrams` | sources |
| `STRUCTURIZR_EXPORTS_SUBDIR` | `--structurizr-exports-subdir` | `exports` | generated files (`module` layout only) |
| `STRUCTURIZR_EXPORT_FORMATS` | `--structurizr-export-formats` | `svg,mermaid` | any of `svg`, `mermaid`, `puml` |
| `STRUCTURIZR_IMAGE` | `--structurizr-image` | `structurizr/structurizr` | pin a tag for reproducible exports |
| `STRUCTURIZR_PLANTUML_IMAGE` | `--structurizr-plantuml-image` | `plantuml/plantuml` | renders the SVGs |

## Notes

- Exports use the automatic layout of PlantUML/Mermaid, not the manual layout you drag in the browser.
- `ddev c4-export` replaces the export folder of a module completely, so removed views disappear.
  Don't put hand-written files there.
- Structurizr's local mode writes `workspace.json` and `.structurizr/` into the diagrams folder.
  `workspace.json` holds the manual layout; add both to `.gitignore` if you don't want them committed.
- Containers run as your host user, so generated files are not owned by root (rootless Docker is detected).
